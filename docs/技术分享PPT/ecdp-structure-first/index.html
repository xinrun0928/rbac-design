phase 01 · 总体架构

七层架构 + 一条请求链路

客户端接入层后台管理端 · 移动端 · 指挥大屏 · 第三方系统 · 运维入口

平台服务层ecdp-upms-biz 用户/组织/角色/菜单/权限/日志
业务服务层duty · plan · event · dispatch · resource · dss · fusion · flood-inspection
基础服务层ecdp-third-party 第三方集成 · ecdp-workflow 工作流
公共能力层ecdp-common-* core/data/security/feign/log/encrypt/sensitive…
数据与中间件层OpenGauss · Redis · Nacos · RabbitMQ · XXL-JOB · S3

客户端 → 网关(验 JWT) → 业务服务(@HasPermission) → 数据库 → ApiResult

进入阶段一，项目结构。先看整体分层，七个层级。

客户端接入层，网关加认证层——gateway 和 auth，平台服务层——upms，业务服务层八个业务，基础服务层——third-party 和 workflow，公共能力层——ecdp-common 一堆，数据与中间件层。

带新人走一遍请求：客户端带 Token 到网关，网关验 JWT 再路由到业务服务，业务服务做 Token 内省加 @HasPermission 权限校验，然后访问数据库，最后统一 ApiResult 返回。

记住三层边界：网关不写业务，Auth 只管认证，业务服务不碰别的服务的数据表。

业务架构。平台有十一个业务域，从值守、预案、事件、调度、资源，到决策、融合、防汛巡查，还有外部集成和流程支撑。

核心是一条应急事件处置闭环：事件接报、研判分级、预案匹配与资源查询、调度指挥与任务派发、处置跟踪、反馈复盘。

每个环节对应服务——event 接报，plan 出预案，resource 出物资，dispatch 派任务，dss 和 fusion 做态势分析。用这个闭环记住服务关系，比背清单有效。

其中 flood-inspection 最复杂，自带业务域权限模型，通过 Feign 和 UPMS 协同。

// 子模块引 BOM 管理的依赖：禁止写版本号 // 禁止抄版本 · 禁止子模块私加 dependencyManagement <dependency> <groupId>cn.hutool</groupId> <artifactId>hutool-core</artifactId> </dependency> // 升级只改 BOM 一处，内部模块版本统一 1.0.0

讲版本治理，这是项目结构里很关键的一页。

根 pom 的 dependencyManagement 依次引入五个 BOM：先是ecdp-common-bom 和 ecdp-apis-bom，再是 Spring Boot、Spring Cloud、Spring Cloud Alibaba 三个官方 BOM。

为什么两层？common-bom 管第三方依赖加公共模块，apis-bom 管业务 API 契约，解耦，升级互不影响。

铁律：子模块引 BOM 管过的依赖，禁止写版本号；禁止抄版本，先查 BOM；禁止子模块私加 dependencyManagement。内部模块版本统一 1.0.0，出现 1.0.1 就算违规。升级只改 BOM 一处，比如 hutool 升版，改一个值。

Maven Profile 环境划分。六个 profile，最常用三个：dev 本地默认、71.95_test 测试、11.14_prod 生产。

每个 profile 里配了 Nacos 地址、namespace、group。理解三层隔离：Maven profile 是编译期选择器，Nacos namespace 区分系统，group 区分环境。

比如 namespace，生产系是 ecdp，开发系是 fetch；group 里 local、jx、local_ky 区分环境。

关键卖点：环境差异只改根 pom 一处，通过 @nacos.xxx@ 占位符打包时注入到每个服务，一个变更点影响 13 个服务。所以不许在子模块里再写一份环境配置。

phase 01 · 配置中心

Nacos 配置统一管理（三层配置 · 无 bootstrap）

# 业务服务 application.yml（本地只留连接信息） spring: application: name: ecdp-dispatch cloud: nacos: username: @nacos.username@ discovery: server-addr: @nacos.server-addr@ namespace: @nacos.register.namespace@ config: import: - optional:nacos:application.yml - optional:nacos:${spring.application.name}.yml - optional:nacos:common-ds.yml
层级配置维护
① 系统级application.yml 全局共享架构组
② 服务专属${服务名}.yml 端口/线程池服务负责人
③ 公共组件common-ds.yml / s3 / rabbitmq组件负责人
没有 bootstrap.yml —— SCA 2025 用 spring.config.import 替代；新增模块禁止引入。
optional: 前缀 = Nacos 无该配置不报错；每个文件可独立热更新；禁止按环境建配置（group 已隔离）。

Nacos 配置统一管理。先说一个点：全仓库没有 bootstrap.yml，Spring Cloud Alibaba 2025 用 spring.config.import 替代了，新模块别引。

每个服务的 application.yml 只写服务名加 Nacos 连接信息，然后通过 config.import 拉三层配置：application.yml 系统级共享，服务名点 yml 服务专属，common 开头的是公共组件，比如 common-ds 数据源。

optional 前缀表示这个配置在 Nacos 里没有也不报错，本地没配也能启动。

还有一条硬约束：禁止按环境建配置文件，比如 application-dev.yml，环境隔离交给 group，别在配置文件名上做手脚。

phase 01 · 配置工程化

配置工程化实践（类型安全 · 加密 · 打包）

// 类型安全配置：@ConfigurationProperties @ConfigurationProperties(prefix = "flood.summary") public class FloodSummaryProperties { // 禁止业务类 @Value 散落注入 private Integer windowHours = 2; } // Properties 类放 config.properties 子包 // @EnableConfigurationProperties 启用 # 敏感配置 Jasypt 加密 password: ENC(加密后的密文) # 打包：-P 切换环境 mvn clean package -DskipTests -P 71.95_test
实践要求
配置绑定@ConfigurationProperties，禁 @Value
敏感加密Jasypt ENC(...)，已全局引入 starter
瘦身打包第三方依赖放 project-libs（maven.thin.skip=false）

配置工程化实践。第一，配置用 @ConfigurationProperties 类型绑定，统一放 xxxProperties 类，禁止业务类里 @Value 散落注入。

为什么？散落的 @Value 不可发现、没类型校验、不能整组刷新。Properties 类放 config.properties 子包，类名以 Properties 结尾。

第二，敏感配置用 Jasypt 加密，写法是 ENC 括号里包密文，项目已全局引了 jasypt-spring-boot-starter。

打包命令就是 mvn clean package 加 -P 环境。这里有个待改进项：现在 profile 里的 Nacos 密码是明文，建议迁到 settings.xml 凭据加 Jasypt，这个后面待办再讲。

phase 02 · AGENTS.md 总纲

编码规范总纲（所有专项的上游）

命名

  • 类 PascalCase · 方法 camelCase
  • 常量全大写下划线
  • DTO 以 Request/Response 结尾
  • 异常以 Exception 结尾

注释 · 强制

  • 类 / 方法 / 属性必须注释
  • 类注释 @author @since
  • 属性注释与 @Schema 一致
  • 禁止废话注释

Service / Mapper

  • @RequiredArgsConstructor 构造注入
  • 禁止 @Autowired 字段注入
  • 业务异常只抛 ServiceException
  • ID 用 IdGenerator.idKey() 雪花

DTO / Request / Response

  • Serializable + serialVersionUID
  • 校验分组 ValidGroup.Insert/Update
  • 日期 @JsonFormat · 敏感 @JsonIgnore

集合使用

  • 条件查询用 LambdaQueryWrapper
  • Stream .toList()
  • Map 去重用 toMap(...,(a,b)->a)

代码复用 · 审查

  • 方法 ≤ 50 行
  • 类 ≤ 500 行
  • 重复代码 > 3 处必须抽取
  • 硬编码提取为常量

技术规范阶段开场。进入编码规范总纲，这是 AGENTS.md 里的总纲，是所有专项规范的上游。挑几条红线讲。

第一，禁止 @Autowired 字段注入，一律 @RequiredArgsConstructor 构造注入。

第二，业务异常只抛 ServiceException，不许抛 RuntimeException，因为全局异常处理器只认它。

第三，主键用 IdGenerator.idKey() 雪花 ID，禁止数据库自增。

另外记住两个数字：方法不超过 50 行、类不超过 500 行、重复代码超过 3 处必须抽取。这些是代码审查的红线。

校验 · 权限 · 返回值（安全红线）

// ❌ 反例：直接返回 Entity（签名泄漏） public ApiResult<SysUser> get() { ... } // ✅ 正例：构造 Response 只放需要字段 public ApiResult<SysUserResponse> get() { // 不含 local_signature / signature } // 权限字符串四段式 @HasPermission("umps:system:user:list") // {产品}:{模块}:{资源}:{操作}
Swagger 三件套作用

接口规范下半部分，重点讲返回值红线。

Swagger 三件套：方法用 @Operation，DTO 字段用 @Schema，GET 对象参数用 @ParameterObject。分组校验用 ValidGroup.Insert 和 Update。

// 实体映射注解模板 @Data @TableName("sys_role") public class SysRole extends BaseEntity { @TableId(value = "role_id", type = IdType.ASSIGN_ID) private Long roleId; @Schema(description = "角色名称") private String name; @TableLogic @JsonIgnore private Boolean deleted; } // create_time 用 FieldFill.INSERT // update_time 用 INSERT_UPDATE

建表先翻数据库设计规范。几个要点。

表名全小写下划线，按模块加前缀，sys_、org_、duty_、plan_ 这样。

每张业务表必须有雪花主键、create_time、update_time、deleted、以及四个签名字段——local_signature、local_signature_version、signature、signature_version，任何表不能省。

phase 02 · 重点 · 数据签名设计规范

为什么需要两道签名

写入双签落库
→
本地优先通过即信
→
本地失败才调外部
→
外部兜底逐条验签
→
均失败判定篡改
维度本地签名 local_signature一体化签名 signature
算法 / 密钥SM2 国密 · 本地管理平台决定 · 外部管理
批量验签支持，上限 500 条不支持，逐条 HTTP
用途列表展示高频验签 · 优先导出 / 审计 / 合规 · 兜底
// 签名 Key 必须走 buildSignatureKey（参数用业务字段） String buildSignatureKey(String orgCode, String orgName); @Override public String buildSignatureKey(String orgCode, String orgName) { String code = orgCode != null ? orgCode : ""; String name = orgName != null ? orgName : ""; // SEPARATOR = "|"，null 转空串，字节级稳定 return code + SignatureConstants.SEPARATOR + name; }

数据签名是平台最有特色的机制，重点讲。

先讲矛盾：一体化签名平台很权威，但它不支持批量验签——列表一百条就要发一百次 HTTP，还有网络依赖。所以加了本地签名做第一道防线。

本地签名 SM2 国密，本地管密钥，批量最多 500 条，列表场景优先用它；一体化签名逐条验，用于导出、审计、合规，是兜底。

验签流程：写入时双签，验证时先本地，通过就信；本地失败再调外部；两个都失败，判定数据被篡改。

签名 Key 必须走 buildSignatureKey，参数用业务字段，拼接用竖线分隔符，不许在业务里自己拼字符串，否则换密钥版本存量全废。

phase 02 · 异常处理规范

异常处理与5 位错误码

// 错误码：服务1位 + 模块2位 + 错误2位 11001 AUTH_CREDENTIALS_INVALID 认证凭据无效 11101 TOKEN_INVALID 令牌无效 11201 PERMISSION_DENIED 无访问权限 20001 ORG_NOT_FOUND 组织不存在 20101 TASK_NOT_FOUND 任务不存在 // 失败响应：HTTP 200 + code 区分 { "code": 20001, "message": "组织不存在", "success": false, "data": null }

异常处理。全局异常处理器 GlobalBizExceptionHandler 统一兜底。

错误码是5 位格式：服务 1 位、模块 2 位、错误 2 位，比如 11001 认证失败、11201 无权限、20001 组织不存在。

重点理解：业务异常返回 HTTP 200，靠 code 区分，系统异常才 500。为什么？HTTP 语义太粗，业务上用 code 精确。所以新人一律抛 ServiceException。

另外提醒一个现状——Sentinel 熔断降级已经引了依赖，但Feign 接口还没配 fallbackFactory，生产上线前必须补，这个前面演进待办也提过。

日志规范，核心是 @SysLog 的四维操作画像。

四个维度：subSystem 产品、funcType 行为、moduleType 资源、operatorType 访问端。每个操作都能回答：谁、在哪个系统、做了什么、从哪端来的。

moduleType 的编码有公式，大类乘 100 加子序号，比如防汛大类是 110，组织就是 11101，这样同一模块天然落在一个区间，好聚合统计。

SubSystemEnum 一套枚举管三件事：日志分类、MQ 路由前缀、错误码前缀。

写入链路：@SysLog 被切面解析，构造 SysAccessLog，脱敏后通过 Feign 存到 upms 的表里。

要点约定

服务间通信规范。Feign 接口统一放 API 模块，命名 Remote 加功能加 Service。

而且必须在 META-INF/spring 的 imports 文件里声明全限定名，漏了就不会注册。内部接口用 @Inner，校验 from=Y 请求头，Feign 拦截器自动加头，防止外部绕过网关直连。

第三方对接有一个铁律：所有外部系统对接必须收敛到 ecdp-third-party，业务服务通过它的 API 调，不让外部变化波及核心。

还有幂等：写操作必须考虑，模板是 Redis setIfAbsent 加数据库唯一约束，撞了 DuplicateKeyException 转成 ServiceException。

延时方案取舍

// 消费者铁律：自动 ACK · 幂等 · 不阻塞 @RabbitListener(queues = "flood.task.created.queue") @MqConsumerLog(...) public void onTaskCreated(TaskCreatedMsg msg) { // 禁止手动 ACK，异常必须外抛 taskService.doSomething(msg); } // NackStrategy 三态 REQUEUE 重入队 · NACK 进死信 · DISCARD 丢弃

消息队列规范。延时队列选了 x-delayed-message 插件，毫秒级精度，比 TTL 加 DLX 准，比数据库轮询省。

命名是三段式：前缀点模块点动作，前缀来自 SubSystemEnum，比如 flood.task.created，跟日志的 moduleType 是同一套枚举。

消息体要求 JSON 序列化、字段带 @Schema、实现 Serializable。

消费者有几条铁律：禁止手动 ACK，用 @MqConsumerLog 自动确认；异常必须外抛；消费者必须幂等；禁止阻塞。失败策略三态：REQUEUE 重入队、NACK 进死信、DISCARD 丢弃。

phase 02 · 数据度量规范（参考性）

单位混用是隐蔽 bug

// ❌ 反例 double lat = 22.543209; // 精度不够 float amount = 0.1f + 0.2f; // ≠ 0.3 int duration = 3; // 分？秒？ // ✅ 正例 BigDecimal lat = new BigDecimal("22.543209"); // 经纬度保留 6 位小数 BigDecimal amount = new BigDecimal("0.30"); // DECIMAL(18,2) + setScale(2, HALF_UP) long durationSec = 205; // 时长存秒 double percent = 0.85; // 百分比存 0-1
三原则说明
存储精度 ≥ 计算精度 ≥ 展示精度底层精度只升不降
口径一致前后端 + 数据库 + 外部单位统一
字段语义标注@Schema(description="距离（m）")
定位：参考性规范（非强制）—— 法规财务 / 外部对接 / 报表精度必须遵守。

数据度量规范是参考性规范，不强制，但提醒别踩坑。

三个原则：存储精度大于等于计算精度大于等于展示精度；口径一致，别前端米后端千米；字段语义标注，@Schema 里写清楚单位。

几个高频点：经纬度用 BigDecimal 六位小数，禁 double；时长存秒；金额绝对禁止 float double，0.1 加 0.2 不等于 0.3，用 BigDecimal 加 DECIMAL(18,2)；百分比内部存 0 到 1 的小数。

写字段时顺手标单位，成本最低收益最高。

技术规范：规范即契约
